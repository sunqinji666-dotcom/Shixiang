# 拾响 AI 功能专项优化执行报告

版本：提案 1.0  
日期：2026-08-13  
适用项目：拾响仓库根目录

## 1. 报告用途

本报告用于交给后续 AI 编程代理直接执行。优化范围严格限定在拾响应用内部的 AI 能力，不调用或操作 Final Cut Pro、Premiere Pro、DaVinci Resolve、剪映、Finder 等外部软件，不执行跨软件拖拽验证，不做画面理解、自动配乐、自动铺音效、联网音效商城或生成式音效。

本轮目标不是增加更多入口，而是让现有本地 AI 形成一个可靠闭环：

> 用户用摄影师或剪辑师的自然语言描述声音需求，拾响正确理解约束，给出高质量候选，解释推荐原因，并帮助用户在应用内更快完成判断与整理。

## 2. 当前 AI 架构判断

当前实现已经具备扎实基础：

- `LocalAISearchPlanner` 使用本地 Qwen 3 1.7B 4-bit，将自然语言请求扩展成最多 10 个检索词。
- `SoundSemanticEngine` 使用确定性分类词典、限定词、创作者意图和时长规则建立本地语义查询。
- SQLite 负责全文召回、中文字符索引、语义概念索引和持久化。
- `LocalAISearchRanking` 混合原名、目录、语义相关度等证据生成重点结果。
- `SoundMetadataSuggestion` 提供中文别名、标签、置信度和识别理由，并允许审核、批量应用和撤销。
- 相似声音同时使用命名家族、语义、时长、BPM、调性和声学指纹。
- 所有音频、索引、搜索词和 AI 结果默认保留在本机。

当前架构的正确方向是“小模型理解请求，确定性引擎召回与排序”，不应改成让语言模型逐条读取数万条声音，也不应把所有决策交给不可解释的模型输出。

主要短板：

1. Qwen 输出目前只有关键词，缺少结构化意图、否定条件、强弱程度和置信度。
2. 搜索理解与最终排序之间缺少统一的数据契约。
3. 结果可以显示“理解到”的概念，但缺少逐条推荐理由和冲突说明。
4. 语义评测以零散回归为主，缺少面向剪辑语言的固定基准集。
5. 智能命名偏向生成显示名，结构化标签体系仍可进一步统一。
6. 声学指纹主要用于“相似”，尚未充分参与自然语言搜索的听感重排。
7. 暂无明确的本地偏好学习契约，也没有让用户查看、关闭和清除学习数据的完整设计。

## 3. 本轮产品原则

### 3.1 必须坚持

- 本地优先，默认不联网。
- 原始音频、文件名和目录保持只读。
- 模型输出必须经过白名单、范围校验和确定性规则约束。
- AI 失败时自动退回现有语义搜索，不能阻塞普通搜索。
- 搜索结果首先追求前 5 条可用率，而不是结果总量。
- 所有 AI 元数据写入前必须可预览、可选择、可撤销。
- 不因 AI 优化破坏三万条以上资料库的启动、搜索和滚动性能。

### 3.2 本轮明确不做

- 视频或图片画面识别。
- 自动配乐、自动铺设音效或时间线编辑。
- 生成音效、生成音乐、语音克隆。
- 操作或自动化任何外部软件。
- 针对某个剪辑软件编写独立插件。
- 将音频、文件名、路径、标签或搜索句上传到云端。
- 在没有评测集的情况下更换模型或增加大型依赖。

## 4. 建议目标架构

将现有 AI 搜索从“关键词扩展”升级为“结构化查询计划”。建议新增以下核心类型，名称可按项目风格调整：

```swift
struct AISearchIntent: Codable, Equatable, Sendable {
    var soundTypes: [WeightedTerm]
    var useCases: [WeightedTerm]
    var emotions: [WeightedTerm]
    var materials: [WeightedTerm]
    var spaces: [WeightedTerm]
    var distances: [WeightedTerm]
    var dynamics: [WeightedTerm]
    var tonalQualities: [WeightedTerm]
    var requiredTerms: [String]
    var preferredTerms: [String]
    var excludedTerms: [String]
    var minimumDuration: TimeInterval?
    var maximumDuration: TimeInterval?
    var targetDuration: TimeInterval?
    var confidence: Double
}
```

处理链路：

```text
用户原句
  → 轻量规则预解析
  → 本地 Qwen 输出结构化 JSON
  → Schema 校验与概念白名单归一化
  → SQLite 文字与语义召回
  → 时长、否定条件、语义和声学特征重排
  → 逐条生成确定性推荐理由
  → 应用内展示候选与解释
```

Qwen 只负责理解用户句子，不接触资料库条目。所有条目匹配、冲突惩罚和解释均由 Swift 确定性实现。

## 5. 优化任务清单

### P0-1：结构化意图解析

目标：让 AI 不只返回关键词，而是返回可验证的声音需求结构。

必须覆盖：

- 声音类别：转场、冲击、环境、拟音、UI、人声、音乐、科技等。
- 剪辑用途：产品落版、Logo 出现、推镜、拉镜、切镜、慢动作、空镜、预告、悬疑铺垫、搞笑节奏点等。
- 情绪：紧张、治愈、压迫、浪漫、神秘、史诗、轻松、危险等。
- 材质：金属、木质、玻璃、纸张、布料、液体、机械、电子等。
- 空间：室内、室外、走廊、地下空间、城市、自然、空旷、狭窄等。
- 距离：贴耳、近处、中景、远处、由远及近、由近及远。
- 动态：上升、下降、推进、爆发、渐弱、突然停止、持续、脉冲。
- 听感：明亮、低沉、厚、薄、干净、粗糙、柔和、尖锐、克制。
- 时长：明确范围、上限、下限、目标值和“左右”的容差。

实现要求：

- 保留现有短查询旁路；“风”“雨”“UI”等不应强行交给模型扩写。
- 紧凑资料库标签继续优先精确检索。
- 模型 JSON 解析失败、超时或输出越界时退回确定性引擎。
- 结构化字段必须经过枚举或白名单映射，未知概念只能进入低权重自由词，不能直接控制强过滤。
- 对相同标准化查询保持会话缓存。

验收样例：

- “产品结尾落版，金属感，一秒左右，不要太炸”应解析出产品落版、金属、目标约 1 秒、中等或偏低强度，并排除强爆炸。
- “远处雷声，不要雨，不要贴脸”应保留天气/雷声，排除雨声与近距离。
- “慢镜头的布料飘动，柔一点，三到五秒”应解析为慢动作、布料、柔和、3–5 秒。
- “机械门关上，尾巴短，别有科幻 UI 感”应解析机械/关门/短衰减，并排除 UI 与强科技提示音。

### P0-2：否定、程度和关系解析

目标：解决“命中了词，却违反了用户要求”的核心问题。

需要支持的语言：

- 否定：不要、别、排除、不要有、不能有、无、非、not、without、no。
- 程度：稍微、偏、有一点、比较、很、非常、极强、克制、不要太。
- 比较：更短、更远、更厚、更干、更亮、没那么炸。
- 关系：由远及近、先弱后强、快速上升后立即停止、金属但不要机械。

实现要求：

- `required`、`preferred`、`excluded` 必须区分。
- “不要太炸”不能简单等于排除所有冲击音，应解释为降低高强度、爆炸和过长低频尾音的权重。
- “金属但不要机械”必须保留材质和排除风格，不可把两个概念一起删除。
- 否定条件默认使用强降权；只有高置信度、明确类别且不会导致零结果时才允许硬过滤。
- 当所有候选均违反某个条件时，仍可显示少量最接近结果，但必须标注“未完全满足”。

### P0-3：统一 AI 排序器

目标：把当前分散的文字、语义、意图和声学证据汇总为可测试评分。

建议评分维度：

```text
总分 =
  原文件名/别名精确证据
  语义概念匹配
  剪辑用途匹配
  时长匹配
  材质/空间/距离/动态匹配
  声学听感匹配
  同家族与命名变体证据
  本地偏好微调（后续启用）
- 明确排除项冲突
- 强约束违反
- 泛化词与噪声词惩罚
```

实现要求：

- 分值组件必须可单元测试，不允许只返回一个无法解释的总分。
- 精确原名命中应保留明显优势，但违反明确排除条件时必须降权。
- 时长目标采用连续衰减，不要只做范围内/范围外二值判断。
- 资料库缺少声学指纹时，结果仍应稳定；不得因未分析而系统性歧视该声音。
- 前 10 条使用完整重排，长尾可继续沿用现有有界策略，避免全库重计算。

### P0-4：逐条推荐理由

目标：让用户知道为什么推荐，以及哪里没有完全满足。

每个重点结果建议生成：

- 1–3 个正向原因，例如“产品落版”“金属瞬态”“0.9 秒接近目标”。
- 最多 1 个警告，例如“力度略强”或“未确认远近”。
- 结果来源标识：原名命中、语义推荐、相似音色或混合证据。

理由必须由评分证据确定性生成，不让 Qwen逐条编写，避免幻觉和额外延迟。

禁止：

- 展示虚假的精确百分比。
- 在没有声学证据时宣称“低频厚重”“瞬态锋利”。
- 把目录上下文误写成音频本身的确定属性。

### P0-5：AI 搜索评测框架

目标：任何 AI 优化都能量化比较，不凭主观印象。

建立至少 100 条固定查询，分类建议：

- 20 条基础对象/动作。
- 15 条剪辑用途。
- 15 条情绪与风格。
- 15 条材质、空间和距离。
- 15 条时长与动态。
- 15 条否定和组合条件。
- 10 条中英混合、口语、错别字和极短输入。
- 10 条故意模糊或互相冲突的请求。

每条评测记录：

- 期望解析出的结构化意图。
- 不应出现的错误意图。
- 最少一个必须命中的概念。
- 最少一个必须排除或降权的概念。
- 可选的合成候选集和期望前 5 排序关系。

核心指标：

- 意图字段准确率。
- 否定条件保留率。
- 前 5 条约束违反率。
- 前 5 条人工可用率（需要孙哥或测试者后续标注）。
- 热搜索延迟与冷启动延迟。
- AI 失败后的回退成功率。

测试应使用构造的 `SoundItem`，不得要求真实音频或外部软件。

### P1-1：声学特征参与自然语言搜索

目标：让“低沉、明亮、尖锐、柔和、瞬态强、尾巴短”等听感词真正影响排序。

现有 `AcousticFingerprint` 已包含频段、明暗、滚降、平坦度、过零率、峰均比、瞬态密度和动态范围。应建立一个透明的听感映射层，例如：

- 低沉：低频占比高、谱质心偏低。
- 明亮/尖锐：高频占比和谱质心偏高。
- 柔和：瞬态密度和峰均比适中或偏低。
- 冲击/干脆：瞬态明显、持续时间短、尾部能量衰减快。
- 粗糙/噪声感：频谱平坦度和过零率偏高。

要求：

- 所有映射应由测试样本验证。
- 使用“倾向”而不是绝对标签。
- 无指纹候选保持中性分，不做负分。
- 不增加全库搜索阶段的音频读取；只使用已有持久化指纹。

### P1-2：智能命名升级为结构化元数据建议

目标：从“生成一个中文名字”升级为“生成稳定、可检索、可复核的内部知识”。

建议将建议结果拆分为：

- 显示别名。
- 主分类与子分类。
- 动作/对象。
- 材质。
- 空间与距离。
- 情绪与用途。
- 动态与强弱。
- 置信度和证据来源。

命名规范建议：

```text
[主体或动作] + [材质/空间/强弱限定] + [必要序号]
```

要求：

- 相同家族的命名结构必须一致。
- 不根据不充分证据臆造空间、情绪或用途。
- 置信度低的字段独立标记，而不是降低整条建议的一个总置信度。
- 批量审核可按“只应用高置信字段”执行。
- 保留现有撤销与原文件只读边界。

### P1-3：查询澄清与零结果恢复

目标：当请求矛盾、太宽或太窄时，在应用内帮助用户修正搜索。

可实现为确定性建议芯片，不需要聊天界面：

- 条件过宽：“结果较多，可补充时长、远近或材质”。
- 条件冲突：“同时要求金属且排除机械，已保留材质并降低机械风格”。
- 结果过少：“没有完全满足全部条件，已放宽时长至 ±0.5 秒”。
- 零结果：提供“移除否定条件”“放宽时长”“仅搜索原名”三个明确动作。

系统必须展示放宽了什么，不可静默篡改用户条件。

### P1-4：本地偏好学习基础

目标：让拾响逐渐理解用户个人审美，但保持可控、可查看、可清除。

第一阶段只建立数据契约与离线重排，不训练模型。可记录：

- 在某个标准化查询下试听某候选。
- 重复试听。
- 收藏或取消收藏。
- 相似对比中的保留或淘汰。
- AI 推荐被用户选择后继续操作。
- 音效从拾响开始拖出（仅记录应用内部拖拽发起，不操作或识别目标软件）。

推荐信号权重：

- 单次试听：弱正反馈。
- 重复试听：中等正反馈。
- 收藏：强正反馈。
- 对比保留：强正反馈。
- 对比淘汰：明确负反馈。
- 拖出发起：强正反馈，但不等同于成功导入其他软件。

隐私和控制：

- 默认仅本机 SQLite。
- 设置页提供关闭学习、查看统计、清除全部学习数据。
- 不保存完整私人项目上下文；标准化搜索可考虑散列或仅保存结构化意图。
- 偏好分只做小幅重排，不能压过明确搜索约束和原名精确命中。

本项建议在 P0 搜索评测稳定后实施，避免用反馈掩盖基础相关性问题。

### P1-5：AI 能力状态与降级说明

目标：用户明确知道当前用了哪一层能力。

建议状态：

- “本地 AI 理解”：Qwen 结构化解析成功。
- “本地语义理解”：Qwen 不可用，确定性语义引擎正常。
- “仅匹配原文”：用户主动选择或语义索引不可用。
- “声学增强”：部分重点候选有指纹参与重排。

不要把所有模式都叫 AI，也不要在本地模型缺失时只显示模糊失败。降级后搜索仍应立即给结果。

### P2-1：搜索词纠错与个人术语

- 支持常见中英文错拼、全半角、繁简体和行业缩写归一化。
- 从用户确认过的命名字典建立个人术语桥接。
- 个人术语必须可编辑和删除。
- 不允许自动把一次偶然输入永久写入词典。

### P2-2：相似声音的意图化控制

在现有“相似声音与变体”中增加可解释方向：

- 更短 / 更长。
- 更轻 / 更强。
- 更近 / 更远。
- 更暗 / 更亮。
- 保持音色，仅改变时长或强弱。

这些控制仅用于应用内候选重排，不生成新声音，也不调用外部软件。

### P2-3：资料库 AI 覆盖与质量诊断

在现有“声音理解中心”中补充：

- 语义元数据覆盖率。
- 声学指纹覆盖率。
- 低置信命名数量。
- 未识别分类数量。
- 疑似错误标签或互相冲突标签。
- 可安全修复项与必须人工审核项。

诊断只读取拾响索引和已有指纹，不在打开页面时扫描音频。

## 6. 推荐实施顺序

第一阶段必须完成：

1. 建立 AI 搜索基准测试集。
2. 定义 `AISearchIntent` 和结构化模型输出 Schema。
3. 实现否定、程度、时长与关系解析。
4. 实现统一评分组件。
5. 实现逐条推荐理由。
6. 完成回退、性能和回归测试。

第二阶段：

1. 将已有声学指纹接入听感重排。
2. 将智能命名扩展为字段级结构化建议。
3. 增加查询澄清和零结果恢复。
4. 增加 AI 状态与降级说明。

第三阶段：

1. 建立本地偏好事件与可清除存储。
2. 用偏好对重点结果做小幅重排。
3. 增加个人术语和相似方向控制。
4. 增加 AI 覆盖与质量诊断。

禁止在第一阶段同时重构整个 SQLite、播放器、波形、资料库扫描或主界面布局。

## 8. 工程约束

- 修改前检查工作树，保留用户已有改动。
- 遵循现有 Swift Concurrency 隔离，不让旧搜索任务回写新结果。
- 模型进程必须有超时、取消和输出大小限制。
- JSON 解码必须拒绝未知顶层结构、超长数组、非法时长和非有限浮点数。
- 搜索输入长度和模型生成长度必须有上限。
- 不在主线程运行模型、全库评分或 SQLite 大查询。
- 不因展示推荐理由而让播放进度或列表滚动触发整库重算。
- 旧 SQLite 数据库应自动兼容；新增持久化表需有迁移测试。
- 不把音频字节、文件名、绝对路径、搜索语句或偏好事件写入诊断包。
- 所有新增 UI 保持 VoiceOver 中文语义，并尊重减少动态效果。

## 9. 第一阶段验收标准

功能：

- 结构化解析覆盖至少 100 条固定查询。
- 明确否定条件在测试中 100% 保留，不被关键词扩展反转。
- 时长上限、下限、范围和目标值都有独立测试。
- 每条重点结果最多显示 3 个真实证据理由和 1 个冲突提示。
- 本地模型不可用、超时、取消、JSON 损坏时均能退回现有语义搜索。
- 清空或快速切换查询时，旧 AI 结果、理由和状态不得回写。

质量：

- 构造候选集中的前 5 条强约束违反率为 0。
- 泛化关键词不能让短查询退化为近全库结果。
- 精确原名命中在无冲突时继续获得优先级。
- 没有声学指纹的条目不会被默认降为低质量。

性能：

- 热查询目标维持亚 100ms 的确定性召回与重排，不包含本地模型首次启动。
- 重排只处理有界候选集，不对三万条条目逐条运行复杂解释。
- 搜索、清空和快速换词期间界面保持可响应。

验证：

- 相关单元测试全部通过。
- 完整 Core、Audio、KeyAnalyzer、PitchShift 测试通过或仅出现项目已有的环境性跳过。
- Debug 与 Release 构建通过。
- 不启动或操作任何外部剪辑软件。
- 不执行任何跨软件拖拽。

## 12. 最终判断

拾响下一阶段最有价值的 AI 升级，不是增加一个聊天框，也不是让模型接管整个资料库，而是把已有“本地语义搜索”升级为一套可解释、可评测、理解剪辑约束的本地检索系统。

优先级最高的产品结果是：

> 用户说“我要什么”和“我不要什么”，拾响都能听懂；前几条候选尽量可用；即使没有完全命中，也明确告诉用户差在哪里。

这会直接强化拾响的核心价值，同时保持软件轻量、本地、安全和专业。
